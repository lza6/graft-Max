# 改进计划（规划文档目录）

> 本目录只放**规划类文档**，不放代码。所有规划文档与仓库实现严格分离，避免"计划混进源码"。

## 目录约定

| 路径 | 内容 |
|------|------|
| `下一步改进指南.md` | **当前有效的下一轮迭代指南**（唯一权威版本，基线见文件头）→ 现为 **v4.0 · 基线 max.10** |
| `archive/` | 已交付或已废弃的历史规划（只读，不再维护） |
| `archive/下一步改进指南-v3-max10-已交付.md` | v3.0 版指南，**N0–N20 全 21 卡已全部落地**（max.10）：P1 缺陷清零、面板拆前端工程、多仓库、后端热插拔、冷启动 20s、CI 门禁 |
| `archive/下一步改进指南-v2-max6-已交付.md` | v2.0 版指南，T1–T10 已全部落地（max.7），T7 npm 发布 blocked |
| `archive/参考对标-差距审计-已归档.md` | 早期"参考对标 / 差距审计"工作底稿（Phase A 只读分析） |
| `archive/参考的结果计划指南.md` | 更早期参考样本 |

## 文档生命周期

1. **新建**：每轮迭代开始时写一份 `下一步改进指南.md`，文件头标注基线与生成时间。
2. **执行**：任务落地时同步更新仓库根目录的 `workflow_status.md`（验收表 + 验证日志），**不要**在本目录里记录执行过程。
3. **归档**：下一轮开始前，把上一轮指南 `git mv` 到 `archive/`，文件名加 `-<末版版本>-已交付` 或 `-已废弃` 后缀。
4. **唯一权威**：任何时刻 `下一步改进指南.md` 只能有一份。历史版本去 `archive/` 找。

## 与其他文档的分工

| 文档 | 职责 | 不写什么 |
|------|------|---------|
| `改进计划/下一步改进指南.md` | 下一轮做什么、为什么、怎么验收 | 不写已完成的历史细节 |
| `workflow_status.md` | 当前进度、验收证据、审查发现 | 不写未来计划 |
| `CHANGELOG.md` | 已发布版本的用户可见变更 | 不写内部规划 |
| `docs-selfdev/改造日志.md` | 每项自研改造的"改了什么/为什么/怎么验证" | 不写未落地的设想 |
| `docs-selfdev/项目约束.md` | 红线与设计规则（违反即返工） | 不写任务清单 |
